# Internationalization

## Model

- `content/pt-BR/**` is the source of truth.
- `content/en/**` mirrors the same relative path and holds an overlay with translatable fields only. The list is declared per type in `lib/schema` (`x-translatable` in the generated JSON Schemas). `body` stands for the Markdown body.
- Structural fields (ids, relations, numbers, lanes, nodes) exist once, in pt-BR, so a translation cannot drift them.
- The loader (`lib/content`) merges the overlay over the pt-BR entity. Arrays of objects merge by index, so structural keys survive.
- A missing overlay means fallback to pt-BR. The site shows a visible marker on fallback pages.

## Stale translations

An overlay carries `source_hash`, the sha256 of the translatable part of the pt-BR source (`sourceHash` in `lib/schema`). When the source changes, the hash no longer matches and the loader flags the entity as stale.

## Overlay example

```yaml
---
id: outbox
tipo: padrao
source_hash: 3f1c...   # sha256 of the pt-BR translatable fields and body
nome: Transactional outbox
quando_usar:
  - First scenario
  - Second scenario
---
English body.
```

## UI strings

The site keeps UI strings in `site/src/i18n/pt-BR.json` and `site/src/i18n/en.json` as flat dotted keys. `tests/i18n` enforces key parity, non-empty values, matching placeholders and that every key the source asks for exists. Field labels use `f.<field>`, entity types `tipo.<tipo>`, layers `layer.<layer>` and `layerdesc.<layer>`, content sections `section.<layer>.<folder>`.

Routes use `/{locale}/...`. `/` redirects by `navigator.language` (pt prefix goes to pt-BR, anything else to en). The header language switcher links to the same route in the other locale, so the current page is kept. An en page without an overlay shows the pt-BR text, a visible banner (`fallback.banner`) and `data-fallback="true"` on `<main>`.

## Adding a language

Add the locale to `LOCALES` in `lib/content`, add its UI strings, and add overlay files under `content/<locale>/`. No structural content changes.
